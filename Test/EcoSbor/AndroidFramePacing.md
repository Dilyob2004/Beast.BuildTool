# Android 10+ и возврат скролла

## Изменения

- NativeActivity использует `AChoreographer_postFrameCallback64` вместо ожидания
  фиксированных 16 ms. На активной поверхности запрашивается один следующий
  callback; обновление выполняется после обработки очереди событий, по display
  timestamp. Интервал не предполагает фиксированные 60 Hz.
- При потере фокуса, паузе и уничтожении поверхности запрос инвалидируется,
  часы сбрасываются. Поздние callbacks проверяют thread-local epoch, не ссылаются
  на уничтоженный stack State. В фоне looper блокируется на событиях.
- Первый кадр после восстановления получает delta=0, большие пропуски ограничены
  100 ms. Input edges сохраняются до обработки реального кадра, а не сбрасываются
  после каждого пробуждения от события.
- UI host не вызывает GPU Submit для неизменившейся ревизии Canvas. Неудавшийся
  Submit повторяется; пересоздание поверхности, redraw, resize и resume требуют
  повторной презентации. Scene::OnUpdate и Tick продолжаются по display callbacks:
  это **не** полная остановка CPU в простое и не damage tracking.
- Скорость отпускания вычисляется по фактическому перемещению содержимого.
  Раньше резиновое сопротивление уменьшало перемещение, но Fling получал полную
  скорость пальца, создавая избыточный импульс после отпускания.
- Фаза кеша карточки нормализуется перед выделением целого пикселя. Погрешность
  перемещения около целого значения больше не переключает эквивалентные фазы
  64/0 и не вызывает лишнюю перерисовку. Пиксельная коррекция скролла и фильтрация
  текста 1:1 сохранены; это не субпиксельная фильтрация движущихся снимков.

## Совместимость

Новые проекты и EcoSbor: `minSdk 29`, Android 10+. Для старого проекта с SDK
нужно поднять `android.minSdk` в Config/BuildConfig.json и `minSdk` в app/build.gradle.
BuildTool сообщает понятную ошибку при API ниже 29. ABI пока **arm64-v8a**;
armeabi-v7a, автоматический выбор GL/Vulkan, виртуализация и memory-pressure
кеш-политика не добавлены этим изменением. Выбор backend в Launch.cpp сохранён.

API 29 выбран для 64-битного timestamp callback, без ошибки переполнения long
старого API на 32-битных устройствах. Это не обещание поддержки 32-битных APK.
Источник: [Android NDK Choreographer](https://developer.android.com/ndk/reference/group/choreographer).

## Проверка

`Run-Tests.ps1` проверяет часовую модель и физику при 30/60/90/120 Hz, reset/stall,
инерцию растянутого списка против независимого расчёта, отсутствие лишних Submit
в простое, события, восстановление RHI, реальные OpenGL/Vulkan на Windows.
`UIRepaintTests` проверяет 80 околонулевых перемещений без повторной растеризации
карточки и сравнение GPU-пикселей кешированного/прямого UI на 9 DPI.

Эти тесты не измеряют кадровую плавность Android-драйвера. На физических Android
10/11 устройствах ещё нужны scroll/release, многократное сворачивание/возврат,
блокировка экрана, длительный простой, frame-time/память/нагрев, отдельно GL и
Vulkan. Стабильные 60/90/120 fps на слабых устройствах не гарантируются.

Проверка 2026-09-19: Windows CPU/OpenGL/Vulkan тесты прошли, Debug/Release APK
собраны; aapt подтвердил minSdk 29 и arm64-v8a. Release — 3,589,395 байт,
unsigned; комплект отдельных символов проверен. Попытка запуска установленного
AVD API 36.1 не дошла до проверки приложения: эмулятор оставался adb offline
и был закрыт. Android 10 runtime и визуальная плавность пока не подтверждены.

## Повторная проверка конца возврата

`ScrollSettleProbe.cpp` воспроизводит возврат главной страницы EcoSbor при
1080×1800, scale 2.625 и 60 Hz. До исправления было 36 перерисовок; после
достижения конечного экранного пикселя ещё 7 кадров строили ту же картинку.
Промахов кеша карточек или глифов при этом не было.

ScrollView теперь сохраняет дробную физику и координаты дочерних элементов,
но запрашивает перерисовку перемещения только при изменении округлённого
экранного смещения. Изменения содержимого, состояния ввода и восстановление
поверхности по-прежнему могут потребовать кадр независимо от перемещения.
После исправления: 25 перерисовок, 0 повторных перерисовок того же пикселя.
CPU-время хвоста в этом локальном тесте снизилось примерно с 0.45 до 0.003 ms.
Это не замер Android GPU и не устранение самой пиксельной ступенчатости.

UIScrollHostTests проверяет обе оси при scale 0.75/1/1.25/2.625/4, дробные
координаты, завершение возврата и смену DPI. Windows CPU/OpenGL/Vulkan тесты
прошли; Android Debug/Release пересобраны, отдельные Release-символы проверены.

Подключён физический Samsung SM-A736B (Android 16, Adreno 642L), Debug APK
установлен поверх существующего приложения. Запуск Activity и загрузка Vulkan
успешны. После разблокировки подтверждены отрисовка главной страницы и реакция
на жесты прокрутки; процесс сохранил PID и фокус, в прочитанном фрагменте его
логов после жестов нет FATAL/ANR. Скриншоты не измеряют плавность: frame-time
на телефоне и субъективная оценка конца возврата ещё не подтверждены.
Также замечено наложение содержимого на системный status bar. Это устройство
не заменяет Android 10.

## Safe area

GameActivity в шаблоне новых проектов и EcoSbor публикует атомарный снимок
WindowInsets: systemBars + displayCutout на API 30+, stable insets + cutout на
API 29. Боковые отступы учитываются так же, как верхний и нижний. Поверхность
остаётся edge-to-edge; UI располагается внутри contentX/Y/Width/Height.
Координаты ввода уже используют эту же область. Системные панели не скрываются.

Нативный поток читает небольшой снимок через JNI перед обновлением кадра;
только изменение отступов вызывает Resized. View API вызывается исключительно
на Java UI thread. Старые проекты без getBeastSafeInsets сохраняют contentRect
fallback: для исправления им нужно перенести обновлённую Activity из шаблона,
сохранив package и собственные настройки.

Windows regression suite (включая safe-area arithmetic и OpenGL/Vulkan) прошёл,
Android Debug собран и установлен. Пользователь подтвердил правильную safe area
на телефоне после разблокировки.
IME/экранная клавиатура этим изменением не реализуется.

## Пиксельная чёткость и анимации

Пользователь выбрал сохранение строго пиксельной чёткости даже при движении.
Округление scroll offset и Nearest 1:1 не отключены; медленная пружина может
удерживать один экранный пиксель несколько vsync, затем переходить к соседнему.
Это не доказательство пропущенных кадров на телефоне. Остаточный пользовательский
лаг остаётся открытым до runtime frame-time замеров.

Общие Button/Pressable получили ease-out состояния hover/focus/press и
smoothstep затухания ripple, Opacity — AnimateTo. Проверены одинаковый прогресс
при 30/60/90/120 Hz, прерывание и прекращение перерисовки после окончания.
EcoSbor CPU/OpenGL/Vulkan suite прошёл, Debug/Release APK собраны, Debug установлен.
На момент повторной попытки runtime-проверки фокус снова у NotificationShade,
поэтому плавность новых переходов на телефоне визуально не подтверждена.

## Замер возврата на физическом телефоне

После разблокировки выполнен adb swipe в EcoSbor на SM-A736B, Vulkan, Debug.
При profiling=true UI host пишет dt Choreographer, CPU BuildFrame, CPU Submit
(включая ожидания) и отложенный GPU timestamp с номером его кадра; gpu=-1
означает отсутствие измерения. По умолчанию эта диагностика выключена.

В участке возврата frame 91–109 измерено примерно 2.3–2.7 ms BuildFrame,
1.1–1.4 ms Submit, 3.0–3.2 ms GPU при dt около 16.6 ms. В начале участка
frame 90: 6.6 ms BuildFrame + 8.4 ms Submit. Это не SurfaceFlinger presentation
trace и не доказательство отсутствия любого jank. Холодный первый кадр намного
дороже и не относится к возврату списка.

В CPU-пробе при scale 2.625 пружина удерживает pixel=-1 на кадрах 24–27, затем
переходит к 0. При 60 Hz это около 67 ms между последними изменениями картинки,
даже если все callbacks обслужены вовремя. Строго пиксельное движение сохраняется
по выбору пользователя; физика пружины в этом диагностическом шаге не изменена.
Подробный лог сохранён в Intermediate/Verification/android-return-profile.log.
Launch.cpp возвращён к profiling=false (значению по умолчанию).

## Сравнение с локальным Flutter SDK и исправление завершения (2026-09-20)

В Prototypes/flutter_application_1/lib/screens/home_screen.dart явно задан
BouncingScrollPhysics; guide/profile также используют его. В локальном
FlutterSDK/flutter/packages/flutter/lib/src/widgets/scroll_physics.dart
toleranceFor использует distance=1/devicePixelRatio и velocity=20/devicePixelRatio.
Beast раньше требовал distance<0.05 dp и speed<0.5 dp/s независимо от DPI.

Теперь Beast завершает пружину при расстоянии <1 физического пикселя и скорости
<20 физических пикселей/сек. Кривая, сопротивление пальцу и пиксельная отрисовка
не изменены. Перед завершением проверяются оба условия, затем происходит один
MoveTo точной границы вместо промежуточного перемещения и повторного MoveTo.
Это сближение критерия завершения, не перенос всей Flutter physics/rendering.

Регрессия EcoSbor 60 Hz, scale=2.625: точный покой на кадре 26 (450 ms) вместо
35 (600 ms). Последняя смена экранного пикселя теперь на кадре 26 вместо 28:
интервал между двумя последними видимыми изменениями 33 ms вместо 67 ms.
Не следует выдавать разницу 150 ms за сокращение видимого лага: часть старого
хвоста уже не меняла картинку. 25 перерисовок, 0 лишних same-pixel кадров.

Windows regression suite, OpenGL/Vulkan и новые проверки DPI/частот/обоих осей/
границ/быстрого пересечения прошли. Android Release собран, символы проверены.
LocalTest/EcoSbor-release-local.apk — отдельная Release-копия, подписанная
локальным Android Debug ключом для установки поверх Debug без потери данных;
это не production-подпись. Исходный unsigned APK и его manifest не изменены.

В local.properties Flutter-примера записан release, тогда как на телефон ранее
ставился Beast Debug. Это не устанавливает режим фактически запущенного Flutter
APK, но требует проверки одинаковых условий перед сравнением производительности.
После подключения SM-A736B тестовый Release установлен через install -r.
Activity успешно запущена, фокус у EcoSbor; выполнен жест растяжения списка.
Субъективная плавность исправления ещё требует оценки пользователя; сравнение
реальных presentation timings с Flutter не выполнено.

## Системная трасса Beast и Flutter (2026-09-20)

На SM-A736B записаны одинаковые adb swipe 80,700 -> 80,1750 за 800 ms.
Beast — установленная локально подписанная Release сборка. Версия установленного
Flutter APK в этом замере не пересобиралась. Не следует сравнивать число кадров
как FPS-бенчмарк: длительность возврата и физика приложений различаются.

Конфигурация: Tests/frame-pacing.pbtxt, анализ: Tests/frame-pacing.sql.
Трассы в Intermediate/Verification: flutter-return.pftrace, beast-return.pftrace,
beast-return-warm.pftrace. Данные анализировались локально, без загрузки на сайт.
Анализатор Perfetto v58.2 скачан из официального манифеста, Windows binary SHA-256:
adfa6bad3d72be3ba9b83fa2b17b69fa13b3ab1cad0f42e52b86188bd5f0f997.
Метод: [Perfetto SQL CLI](https://perfetto.dev/docs/getting-started/command-line-analysis).

App FrameTimeline строк для обеих нативных поверхностей в этой трассе нет.
Используются timestamps SurfaceFlinger latchBuffer: принятие нового буфера,
не точный scanout и не время рисования GPU. Системный status bar исключён.

Весь жест с возвратом:
- Flutter: 92 интервала, среднее 16.63 ms, максимум 18.35 ms, 0 интервалов >25 ms.
- Beast: 66 интервалов, среднее 19.39 ms, максимум 34.39 ms, 11 интервалов >25 ms.
- Beast повторно прогретый: 65 интервалов, среднее 19.38 ms, максимум 34.73 ms,
  11 интервалов >25 ms. Холодным запуском эта разница не объясняется.

После последнего доставленного touch event прогретый Beast передавал буферы
каждые 15–17 ms до отметки ~404 ms. Далее интервалы 32.83 и 33.03 ms, последний
16.73 ms; конец около 486 ms. Flutter продолжал интервалы ~16–17 ms до ~784 ms.
На записанном возврате нет длительного провала cadence в начале/середине.
Две паузы в хвосте согласуются с pixel-snapping и CPU-регрессией, но одна трасса
не доказывает отсутствие всех других причин задержек/дрожания на любых жестах.

Физика и рендерер в этом диагностическом шаге не изменялись. Для покадрового
разделения причины пропусков нужны синхронные маркеры UI offset/revision/Submit
в той же системной трассе. Предпочтение пользователя о строго пиксельной
чёткости сохраняется; субпиксельный режим самовольно не включён.

## Субпиксельный вариант после согласия пользователя

Добавлен ScrollRasterization::Subpixel, включён в страницах EcoSbor и горизонтальной
статистике. PixelAligned сохранён как исходный режим SDK. Снята компенсация дробного
scroll offset и целочисленное округление SDF-фигур внутри нового режима; hit testing
использует прежнюю дробную геометрию. Paint state восстанавливается после списка.
Снимки RepaintBoundary внутри него обходятся: страница не растягивается.

Первый вариант с текстовыми фазами 1/64 оказался регрессией: 36 интервалов >25 ms
на 42 интервала в трассе beast-subpixel.pftrace, среднее 34.53 ms. Он заменён.
В итоговом варианте текст рисуется в родном разрешении, фазы ограничены 1/8 px,
ошибка позиции <=1/16 px. Coverage baked в глиф, выборка Nearest 1:1 сохранена.

beast-subpixel8-warm.pftrace: после последнего touch event 41 показ нового буфера,
интервалы 15.66–17.92 ms до ~675 ms; пауз 33 ms в хвосте нет. Весь жест всё ещё
имеет 11 интервалов >25 ms во время движения пальца (синтетический adb swipe).
Холодный прогон beast-subpixel8.pftrace имел максимум 78.87 ms во время жеста,
поэтому полного решения cold-cache jank не заявляем. Нельзя выдавать улучшение
хвоста за полную оптимизацию всего UI.

Windows CPU/OpenGL/Vulkan suite прошёл. Проверены обе оси, DPI, восстановление
pixel grid после subpixel scope, покадровая перерисовка дробного движения и
не более 8 prepared-run фаз для вертикального перемещения одной строки.
CPU ScrollBench Debug: median 1.537 ms / p95 9.615 ms (холодные фазы), против
9.445 / 10.345 ms у первоначального 1/64 subpixel варианта. Это не GPU-замеры.
Legacy ScrollSettleProbe явно оставлен PixelAligned.

Release APK пересобран, символы проверены. Подписанная локальным debug-ключом
копия LocalTest/EcoSbor-subpixel.apk установлена на SM-A736B. Статический
скриншот android-subpixel.png проверен; окончательная субъективная оценка
плавности/чёткости оставлена пользователю.

## Пакетные Vulkan uploads (2026-09-20)

Обнаружено ожидание queue.waitIdle после каждой новой immutable-текстуры.
Версии страниц атласа тоже новые текстуры, поэтому это происходило и во время
скролла. Теперь Prepare отправляет их пакетами: одно ожидание на 8 MiB staging
payload / 128 изображений; крупное изображение — отдельный пакет. Буферы живут
до завершения загрузки, при ошибке незагруженные entries удаляются из cache.
Полностью асинхронной загрузка пока не стала; создание изображений и растеризация
глифов этим изменением не устранены. Физика/качество текста в этом шаге не менялись.

Итоговая Release установлена на SM-A736B:
`Binaries/Android/Release/LocalTest/EcoSbor-upload-batch.apk` (локальный debug-ключ).
Тот же adb swipe, SurfaceFlinger latchBuffer, файлы в Intermediate/Verification:

- beast-upload-batch-cold2.pftrace: 74 интервала, mean 19.76 ms, max 67.89 ms,
  11 >25 ms. После последнего touch: 41 буфер, интервалы 15.55–17.63 ms до 673 ms.
- beast-upload-batch-warm2.pftrace: 77 интервалов, mean 18.97 ms, max 49.89 ms,
  10 >25 ms. Первый интервал, пересекающий отпускание, 32.23 ms; затем
  39 интервалов 15.69–17.47 ms до 678 ms.

Предварительная beast-upload-batch-warm.pftrace снята до добавления ограничения
128 маленьких текстур: 77 интервалов, mean 18.81 ms, max 53.78 ms, 9 >25 ms.
Первая beast-upload-batch-cold.pftrace не захватила жест и исключена из сравнения.
Нельзя считать разницу одиночных максимумов доказанным ускорением: cold-cache
stalls и отдельная задержка на отпускании остаются. Следующий замер должен
разделить CPU raster/Prepare/upload/present в той же трассе, чтобы не угадывать
оставшуюся причину по одному общему интервалу.

Проверки: Windows Debug и Android Release сборки; EcoSbor CPU/OpenGL/Vulkan suite;
RHIResourceTests с 130 tiny textures, границами 8 MiB, изображением 16 MiB,
вложенным слоем, retirement/replay/device recreation; UIGlyphAtlasTests на 9 DPI,
GL pixel reference и Vulkan validation. Все прошли, VUID сообщений в Windows
логах нет. В просмотренном хвосте Android logcat после жестов fatal/VUID нет
(это не доказывает наличие validation layer на телефоне). Release symbols/hash
проверены. Полного устранения jank по этим данным не заявляем.

## Разделение CPU / Vulkan / доставки ввода (2026-09-20)

Добавлены SDK-маркеры `Core/Trace.h` на основе
[Android NDK ATrace](https://developer.android.com/ndk/reference/group/tracing).
Они активны только при системной трассировке приложения; Windows — no-op.
Scopes закрываются RAII, включая исключения/ранний return; текст приложения
не записывается, используются фиксированные имена. Android минимум API 29
сохранён. Для API 29/30 недебажной сборке может требоваться opt-in
`<profileable android:shell="true"/>`; публичные шаблоны ради этого не изменялись.

Конфигурация `Tests/render-stages.pbtxt` записывает 10 секунд, 32 MiB,
ATrace и sched_switch/sched_waking. Анализ:


**Холодный запуск — beast-stages-cold.pftrace.** Самый долгий UI кадр 30.639 ms:

| Этап | Время, ms | Примечание |
| --- | ---: | --- |
| Build | 16.461 | 14.470 ms Running, 1.992 ms Runnable |
| Text.Resolve | 13.401 | Внутри Build |
| Vulkan Prepare | 11.797 | Создание новых изображений/ресурсов и загрузки |
| UploadWait | 0.343 | Внутри Prepare |
| FrameFence | 0.026 | Ожидание предыдущего GPU кадра |
| Acquire / Record / Present | 0.271 / 0.590 / 1.002 | CPU wall time |

По всей холодной трассе FrameFence max 0.053 ms, UploadWait max 1.593 ms.
Здесь bottleneck — преимущественно CPU-подготовка текста и новых ресурсов,
а не долгое ожидание предыдущего GPU кадра. Это не измерение скорости шейдеров
и не доказательство отсутствия GPU bottleneck во всех сценах.

**Прогретый запуск — beast-stages-warm.pftrace.** Новых upload batches нет,
Prepare max 0.656 ms. В устойчивой части возврата UI.Frame ~2.27–2.60 ms,
Build ~0.94–1.12 ms. Самый тяжёлый кадр всей записи 12.511 ms, во время drag.
Пауза latchBuffer около отпускания 33.40 ms объясняется последовательностью:

| Относительно SDK TouchUp, ms | Событие |
| ---: | --- |
| -28.976 | UI.Frame: 0.197 ms, без Submit (UI не изменился) |
| -28.228 | Приходит следующее событие движения — после обработки кадра |
| -11.408 | Следующий UI.Frame: 7.873 ms, новая позиция отправлена |
| 0 | Завершён SDK TouchUp |
| +4.466 | Первый UI.Frame возврата: 7.836 ms |
| +4.670 | SurfaceFlinger принимает буфер предыдущего Submit |
| +20.397 | Следующий UI.Frame: 2.350 ms; дальше ровный cadence |

Значит именно этот интервал 33 ms нельзя считать 33 ms работы рендера после
отпускания: ему предшествует кадр без новой позиции. Синтетический adb ввод
может приходить несинхронно с vsync; для естественного жеста потребуется отдельный
замер. Не следует «лечить» это отправкой одинаковых кадров — движения не добавится.

В этом шаге добавлена диагностика, физика/семплирование ввода и кеши не менялись.
Следующая оптимизация по измерениям: ограниченный прогрев текстовых фаз и
переиспользование GPU ресурсов атласа; отдельно input resampling на время кадра,
с корректным прекращением предсказания на TouchUp/Cancel. Не объединять эти
изменения в один эксперимент: иначе нельзя определить источник улучшения.
